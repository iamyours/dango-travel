# 协作约定

给同时改这个仓库的人和 agent 用。进度以 [TASKS.md](TASKS.md) 那一行字为准，阶段目标以 [ROADMAP.md](ROADMAP.md) 为准。

## 开始之前

1. `git fetch origin`，然后 `git checkout main`，再 `git pull origin main`。
2. 从更新后的 `main` 看任务板。不要在过期的本地分支上认领。
3. 选一行 **状态** 为 `待认领`、**负责人** 为空、**依赖** 里每一项都已是 `已完成` 的任务。
4. 阶段 3 还要满足开工门禁：说明里已经有维护者写的 `数据门槛已满足：`。没有这句话就不要认领。
5. 阶段 2 一次只开一包目的地。包 A 的三个目的地（P1-11、P2-01、P2-02）还没完成时，不要认领包 B 及以后的目的地。系统任务按任务板末尾的建议顺序，不要跳着认领。
6. 首发前按 [ROADMAP.md](ROADMAP.md) 末尾的 20 步认领。信息架构（P0-11、P0-15）还没完成时，不要先写新手引导。P0-17 的可用性验收没通过时，不要开始 Capacitor（P1-01 起）。
7. 说明以「调整：已并入」开头的行不要认领。

一个人同一时间只拿一个未合并的任务。一个分支只做一个 ID。

## 认领

认领本身就是一次只改任务板的提交，发生在写功能代码之前。

1. 从最新 `main` 建分支，名字是 `task/<ID>-<slug>`。`<slug>` 用小写英文和连字符。  
   例：`task/P0-05-sfx-pack`
2. 只编辑 [TASKS.md](TASKS.md) 里那一行：
   - **负责人**：你的名字或 agent 名
   - **状态**：`进行中`
   - **更新时间**：当天，格式 `YYYY-MM-DD`
   - **分支/PR**：先写分支名；PR 打开后再补链接
3. 提交并推送，打开一个 PR。这个提交里不要夹带功能代码。
4. PR 标题带任务 ID，例如 `P0-05: claim sfx pack`。

两人同时改同一行会产生冲突。冲突时后推的人让出，改回待认领，另选一行。不要在冲突里覆盖别人的名字。

平台若强制分支前缀，仍然要让 ID 出现在分支名里，并在「分支/PR」写下真实分支名。默认名字是 `task/<ID>-<slug>`。

## 状态

| 状态 | 什么时候写 |
| --- | --- |
| 待认领 | 没人做。负责人为空，更新时间为空。 |
| 进行中 | 已经按上面的步骤认领，代码还不能请人合并。 |
| 待评审 | PR 已打开，你认为可以合并。分支/PR 列有链接。 |
| 已完成 | 含该功能的 PR 已经进 `main`。不要在还没合并的 PR 里把自己写成已完成。 |
| 阻塞 | 你继续不了。状态列只写 `阻塞`。说明开头写 `阻塞原因：…`，并写明在等哪个 ID、哪条外部结论或哪一份素材。 |

合并进 `main` 之后，原负责人再开一个只改这一行的小 PR：状态改为 `已完成`，更新时间改为合并日，分支/PR 保留已合并的链接。标题例如 `P0-05: mark done`。

## 不要抢走别人的任务

负责人不是你，且状态是 `进行中`、`待评审` 或 `阻塞` 时，不要改那一行，也不要在平行分支做同一件事。

只有同时满足下面两点才可以接手：

- 行内更新时间早于 7 天；若更新时间为空，视为已经过期。
- 所链 PR 在这 7 天里没有新提交，也没有人回复还在做。以「更新时间」和「PR 最近活动」里较新的一个为准。

接手时在说明里加一句：`接手：原负责人 <名字>，原更新时间 <YYYY-MM-DD>，原因：超过 7 天无更新。` 然后把负责人改成你，更新时间改成今天。在 PR 正文里同样写明接手。

## 写代码时

- PR 保持只解决这一行任务。不要顺手做下一行，也不要夹带无关格式化。
- 主逻辑在单文件 `index.html` 里。同时改它的人要勤把 `main` 合进自己的分支。能拆到 `assets/i18n`、新图片、`koi/` 或文档的，就不要扩大 `index.html` 的改动面。
- 玩家能看见的新文字，同时写入 `assets/i18n/zh.js` 和 `assets/i18n/en.js`，代码里用 key。不要新增硬编码中文。
- 每个内容包最多增加 2–3 个目的地。室内房间、皮肤、氛围变体不算在这 2–3 个里。
- 广告只保留玩家在商店里主动观看的一个激励位。不要加横幅、插屏、开屏、排行榜、PvP、体力或惩罚。
- 不要改 `ads.txt`，也不要改 `index.html` 里的 AdSense 脚本，除非你认领的就是 P1-07 或 P1-08，并且该 PR 写明网页版和 App 版各自怎么走。
- 版号、软著、开发者认证、正式防沉迷是外部行。不要在功能 PR 里收集身份证号。

## 本地先跑再开功能 PR

用静态服务器打开，不要用 `file://`。在仓库根目录：

```bash
python3 -m http.server 8765
```

然后至少点一遍这次改动涉及的路径，例如：

- 主游戏：<http://127.0.0.1:8765/>
- 锦鲤池：<http://127.0.0.1:8765/koi/>
- 若改了语言：中文和英文各走一遍新文案

把你实际点过的步骤写进 PR。只改文档时，说明「未改游戏文件」即可，不必为文档启动服务器。

## `main` 必须随时能部署

两件事会把 `main` 上的游戏文件公开出去：

1. 每小时有任务把本仓库 `main` 的 `index.html`、`assets/` 和 `koi/` 复制到 `iamyours.github.io` 的 `master`。
2. 本仓库的 `.github/workflows/pages.yml` 会在推到 `main` 时部署同一批文件（另外还有 `ads.txt` 和 `.nojekyll`）。只改 `docs/` 或 `README.md` 也可能触发这次部署，但站点内容不包含 `docs/`。

因此：

- 合进 `main` 的 `index.html`、`assets/`、`koi/` 必须是能打开的。
- 半成品放在 `task/...` 分支，不要直接推到 `main`。
- 不要把只在本地能跑的 CDN 删除、坏掉的资源路径或未完成的存档迁移留在 `main`。

## PR 正文建议

```text
任务：P0-05
做什么：
怎么验收：
本地验证：（静态服务器上点过的路径；纯文档则写未改游戏文件）
i18n：（新增了哪些 key，或写没有新文案）
```
